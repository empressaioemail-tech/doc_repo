# Thesis parity ledger

The atom and calibration thesis is implemented twice: the real estate spine (Hauska/Empressa stack, TypeScript/Postgres, repos hauska-atom-contract, hauska-engine, legacy-design-tools, hauska-mcp-server) and the trading vertical (Empressa Cockpit, Python/Postgres, repo empressa-trading, path `apps/cockpit/backend/app/spine/`). The two share zero code and share one theology. This ledger is the single document that keeps the two representations in sync.

Rule: when either vertical lands a finding, breakthrough, or improvement in a spine-model concept, one entry lands here (a parity-table row update plus a findings-log entry). The other vertical's next planning session reviews unadopted entries. The trading repo feeds this ledger via `docs/PARITY_NOTES.md` in empressa-trading; the doc_repo planner reconciles that feed into this file. Nothing else about the two systems is kept in sync; they remain separate ventures with separate infra (per `_catalog/repo_intents.md`), sharing only the atom spec and this ledger.

## The shared theology (implementation neutral)

1. All knowledge is captured as atoms: append-only observations with provenance, citation, confidence, access policy, and time.
2. Confidence is typed with a basis (asserted vs earned); earned claims require proof; asserted claims carry provenance and are never displayed as bare numbers.
3. Predictions pair with outcomes in an append-only evidence ledger; calibration is computed from the ledger with an honest fallback when sparse; calibrated confidence feeds back into serving.
4. Derived atoms carry lineage to their input atoms; calibration without lineage is rejected.
5. Access policy is enforced at one gate; tenant-private data never pools into shared or public aggregates.
6. Data-source license terms are atom-level facts enforced mechanically, not doc-level policy.
7. Absence claims state where the system looked (verified absence), never bare "none found".
8. Application surfaces are composed tiles over the spine; a workspace is a chosen set of tiles; nothing is rebuilt per customer.
9. Functions ship dual interface: app UI plus agent-consumable tools.
10. Capture runs on durable, idempotent, observable jobs, never fire-and-forget scripts.
