# OPS-25 — Cloud infrastructure and cost program: plan of record

## Why this document exists

A 2026-09-16/17 session verified the live GCP bill (August: $1,955.47, Cloud Run trending 171% month-over-month, run rate heading toward $3,000-4,000/mo), found that six always-on Cloud Run services account for roughly 97% of Cloud Run spend regardless of the "the factory is heavy" assumption (all 39 factory/onboarding Cloud Run Jobs together are ~1.3% of it), confirmed the actual service call graph from live deployed env vars rather than names, and stood up DigitalOcean tooling (doctl, `do-apps`/`do-droplets` MCP servers) fleet-wide. None of this had a plan-row, so none of it was scoped. This document is that row.

**Definition of done, this program's first arc.** The six always-on services (hauska-retrieval-api, hauska-engine-api, smartcity-api, cortex-api, smartsite-mcp, hauska-mcp-server) running on DigitalOcean with the GCP originals decommissioned, each cutover verified by a bake period with matching error rate and latency, zero customer-facing downtime. A status claimed by narration instead of a live probe or a bill line fails.

## Governing rules

1. **No dispatch without a row.** Every dispatch names `PLAN-ROW: D-xx`. Enforced by `scripts/dispatch.mjs` and the canon-gate hook through `_catalog/plan_registry.json`.
2. **Migration order is leaf-to-root by verified call graph, not by name or by cost rank alone.** hauska-retrieval-api and smartcity-api have no internal caller found in any of the six services' live env vars — they move first. hauska-engine-api is called by hauska-mcp-server and cortex-api — it moves once its callers' env-var cutover is proven. cortex-api additionally calls a private IP (`10.128.0.2`, the `overpass-tx-01` VM) — it does not move until that dependency is resolved (co-migrate the VM or give it a public IP with a source-restricted firewall rule). hauska-mcp-server is the aggregator with the most fan-out and is customer-facing (paying MCP clients) — it moves last, and only after `mcp.hauska.dev` is live in front of the GCP original so the eventual cutover is a DNS change, not a customer reconfiguration.
3. **Every cutover keeps the GCP original running, unmodified, through a bake period before decommission.** Rollback is reverting the one env var (backend-to-backend) or DNS record (smartcity-api's `smartcityos.io`, hosted at GoDaddy) that was changed. No row closes until the bake period is observed clean.
4. **DNS-based cutovers lower TTL a day ahead of the actual switch**, execute the record change deliberately, and watch both origins' logs during propagation.
5. **Statuses re-grade only by instrument**: live request logs, live latency/error-rate metrics, or a bill line — never a report of intent.
6. **DO tooling is fleet-wide already** (`_state/shared/STANDING_DECISIONS.md`, 2026-09-17) — no row needs to re-provision doctl or the MCP servers.
7. **A new host's egress IP is part of the deployment and must be verified against a control host.** Found on D-5: `municodemeetings.com` (and by extension any third-party government or vendor site with WAF protection) blocks some DigitalOcean IPs and not others, per-IP rather than per-provider or per-region. Before trusting any new droplet or app's outbound calls to a third-party site, test from a second host in the same account and region as a control — that separates "the site blocks DigitalOcean" from "the site blocks this one address." A blocked host is rebuilt on a fresh address, not repaired in place.
8. **DigitalOcean-to-GitHub is connected, scoped to `smartcity-os` and `smartcity-dashboards` only** (operator, 2026-09-17). Widening it to the Hauska-substrate repos is a separate decision for when D-3 resumes, not a default.
9. **A config-only cutover is only durable if it survives the repo's own deploy path.** Found on D-11 (2026-09-17): `hauska-mcp-server`'s `cloudbuild-mcp.yaml` carries `_DASHBOARDS_BACKEND_URL` and sets `DASHBOARDS_BACKEND_URL` on every build via `--set-env-vars`, so an env-var-only flip on the service is silently reverted by the next Cloud Build deploy. Any row that flips an env var on a service with a committed deploy template must change the template in the same unit of work, and must then read the value back off the serving revision. A flip the next deploy undoes is not a cutover, it is a delayed outage. Operator ruling 2026-09-17 (A-3). **A second, related trap found on the same row:** the service's traffic can be pinned to a revision BY NAME rather than following `latestReady` — `gcloud`'s own success message ("revision X has been deployed and is serving 100 percent of traffic") is true of the OLD pinned revision and conceals that a new revision came up `Ready=True` but `Active=False`. Read the traffic spec by field before trusting a deploy message; a canary (`--no-traffic --tag`, verify, then shift) is the safe pattern on a traffic-pinned service.
10. **Verify a cutover from a vantage point that cannot lie to you, and never trust a status field over an observation.** Found on D-9 (2026-09-17): this fleet host has TLS-interception middleware that re-signs every certificate, so a local handshake check cannot distinguish DigitalOcean's certificate from Google's — it would have reported a confident wrong answer. Direct HTTP checks against `*.ondigitalocean.app` from this host also failed with connection resets that did not occur from GCP Cloud Build. Validate from a vantage point outside the local network (D-9 used Cloud Build) and distinguish origins by an unfakeable signal — an edge header (`server: cloudflare` vs `server: Google Frontend`), not a local resolver or a local TLS handshake. Separately: an API status field that has merely stopped changing is not evidence a process stopped — DigitalOcean's certificate API read as permanently failed while its ACME agent was silently retrying every 5-11 minutes the whole time. Count events in a log before declaring a retry loop dead.
11. **A byte-identical response can misread as diverged if framing is compared as payload.** Found on D-9: Cloud Run sets `Content-Length`, DigitalOcean App Platform streams chunked — the same bytes, different transport framing. Any endpoint-comparison instrument for this program must classify payload and framing separately, or a clean migration will read as a failed one.
12. **DNS and domain management are outside this program's DigitalOcean token by design, confirmed twice.** `doctl compute domain list` / `domain records list` and DO's Reserved IP and Container Registry APIs all refuse this token (403) — this is deliberate scope minimization, not a bug to route around. Every DNS change in this program is executed by the operator, by hand, at GoDaddy. Do not request a token widening for this reason; request the operator's hand instead.

13. **A DigitalOcean deployment can report success and run a stale commit, so read back the commit it is actually running.** Found on D-12 (2026-09-17): a deployment reported `build=SUCCESS deploy=SUCCESS`, went ACTIVE on branch `main`, and was serving `f776b4bf` when `main` was `3d3ec62a`. Nothing in the deployment record said so; only a byte comparison of served assets caught it. **Every repoint or rebuild of a DO app must read back `services[0].source_commit_hash` and compare it to the intended commit**, and the remedy when they disagree is `POST /v2/apps/{id}/deployments` with `force_build`. This is the DigitalOcean analogue of rule 9's Cloud Run traffic pin: in both cases the platform's own success message is true of something other than what you asked for.
14. **Do not read a DigitalOcean certificate or domain status to decide whether a cutover is working, and never attach a domain before its DNS record resolves.** Found on D-12, and it compounds rule 10's certificate-API warning. Attaching a hostname that has no record starts ACME retries against a name that cannot validate, which fires the app's own `DOMAIN_FAILED` alert at the operator for a hostname they have not created yet. Order is: create the record, let it resolve, then attach. Where a hostname is Cloudflare-proxied, edge headers stop discriminating origin at all, so a behavioural marker in a response body is the only honest origin test.
