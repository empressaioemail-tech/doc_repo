# AI-memory substrate — feasibility, evidence, and honest go/no-go

This develops the 2026-07-23 placeholder thread into a decision doc. It is read-only research, verified against live source (gh api against `empressaioemail-tech/{hauska-engine, hauska-atom-contract, hauska-mcp-server}` on main, npm) and real market sources. It does not build anything. Every load-bearing claim is tagged PROVEN (seen in live code or on a vendor's own docs), INFERRED (deduced from adjacent code), or UNKNOWN. The value of this doc is a truthful verdict, not a pitch, so it is adversarial about our own idea where the evidence is adversarial.

Bottom line up front: the substrate IS a genuine domain-neutral cited system-of-record spine, and most of the machinery a memory use needs already exists and is generic. But two things the placeholder treated as strengths do not survive contact with the evidence. First, the last mile from "a document is ingested" to "an external agent can put/get/search/traverse memory through the gate" is unwired in live code (the ingest table and the served table are disjoint). Second, the market differentiation as written ("cited, tenant-sovereign, provenance-carrying vs commodity vector memory") is mostly table stakes, not an open gap. The recommendation is a conditional GO scoped to a narrow, honest wedge, gated behind one cheap PoC that tests the riskiest assumption. Details below.

## 1. Code reality — what a generic memory use reuses as-is vs. what is net-new

The question the placeholder's honest-seam #1 raised was "domain-neutral substrate, new schemas" vs "new infrastructure." The evidence lands firmly on the first, with one important correction: there is a real net-new piece that is not just a schema.

### Reuses as-is (domain-neutral, verified in live code)

The content-addressed durable ingest pipeline is domain-neutral end to end. `DocumentIngestService.ingest()` takes arbitrary bytes or a blob-ref, pins them content-addressed, classifies, runs the winning adapter, stamps provenance plus confidence plus accessPolicy, and persists idempotently without ever throwing (`hauska-engine/packages/document-ingest/src/ingest.ts`). The blob store derives the CID as `bafydoc-<sha256hex>` and dedups on content hash (`gcs-blob-store.ts`). Migration 004 creates `document_blobs` (cid PK, content_hash unique, access_policy default tenant-private) and `document_ingest_atoms` (atom_did PK, entity_type as free text, source_document_cid, atom_json jsonb) with no property columns. PROVEN. Crucially, a generic adapter already ships: `GenericPdfAdapter` is the always-registered fallback that extracts text and mints one domain-neutral `document-derived-claim` atom per line or paragraph, and an unknown document routes to it rather than hard-failing (`document-ingest/src/adapters/generic-pdf.ts`, `packages/atoms/src/document-instances.ts`). So you can POST an arbitrary non-property PDF or text file today and get atoms out. PROVEN.

The atom contract's core is genuinely domain-neutral. `entityType` is an open literal string, not a closed property enum; `domain` is a free grouping string; there is no property enum anywhere in the contract (`hauska-atom-contract/src/registration.ts`). `AccessPolicy` is exactly the five-value union the placeholder claims: `public-free`, `public-paid`, `platform-internal`, `tenant-private`, `tenant-shared` (verified directly in `registration.ts`). Confidence is three-axis widthed and minted as `kind: "asserted"` (never "calibrated" at mint), shaped to flow into the calibration overlay. Provenance and CID fields ride on every document-derived atom. PROVEN. The contract's own README states the dividing line precisely: "this package owns the registration mechanism and the contract; consumers own the per-atom instances." That is the structural proof for the placeholder's central claim — a memory atom kind is one `AtomRegistration` plus one Zod schema in a consumer package, not new infrastructure. PROVEN.

The MCP gate's access machinery is fully generic. Four gates confirmed on deployed main: public, codex, map, reporting (the doc set's older "cortex" gate name is retired). `canReadAccessTarget(subject, target)` switches purely on the five-value accessPolicy against tier plus tenant, with zero entityType or property coupling; a memory atom carrying any accessPolicy is gated correctly with no code change (`hauska-mcp-server/src/access-policy.ts`, `product-gates.ts`). `get_atom` accepts any DID with an open entityType. PROVEN.

Graph traversal is real and queryable, not aspirational. `atom_links` is a real table (from/to/link_type PK, indexed both directions); `PgStorage.traverse` and `traverseInbound` are implemented SQL; and the path is exposed end to end through retrieval `atom-trace.ts`, the `GET /atoms/trace/:did` route, and the public `atom_trace` MCP tool (`storage/migrations/005_atoms_storage_port.sql`, `storage/src/pg-storage.ts`, `mcp/src/tools.ts`). `LinkType` is a fixed 15-value vocabulary including `supersedes`, `amends`, `derives-from`, `cites` — richer than ADR-010's initial set and generic enough for memory edges. PROVEN.

The append-only hash-chain history is implemented in-contract, not just specced. `PostgresEventAnchoringService.appendEvent` writes to `atom_events` with `prev_hash` to `chain_hash` (deterministic SHA-256), serialized gap-free per entity via an advisory lock, verbatim JSONB payload the framework does not interpret (`hauska-atom-contract/src/history.ts`). PROVEN. The `temporal/interval-query.ts` primitive implements a real as-of visibility filter (`valid_from <= asOf`, with explicit anticipatory-atom handling), so the "what did we know when" query has a live contract-level implementation. PROVEN.

### Net-new (not just a schema — real wiring)

This is the correction to the placeholder's optimism. Four things must be built; the first is the load-bearing one.

The read bridge does not exist. Document-ingest atoms land in `document_ingest_atoms`, but the gate's generic read tools (`get_atom`, `search_atoms`, `atom_trace`) resolve through `StoragePort`, which is typed to `StoredAtomInstance = CodeAtomInstance | PropertyAtomInstance` over the separate `atoms` and `atom_links` tables (`hauska-engine/packages/atoms/src/property-instances.ts`, `hauska-mcp-server/src/tools.ts`). The write table and the served table are disjoint, with no `StoragePort` bridge and no document-atom read route. So today you can ingest an arbitrary document and mint atoms, but an agent cannot retrieve or traverse those atoms through the gate. `search_atoms` further pins entity_type to a `CODE_ENTITY_TYPES` enum client-side. PROVEN. This is the single most important finding in the audit: the substrate can eat documents and can serve atoms, but the pipe between those two halves is not connected for anything outside the code/property tables.

A memory-shaped agent write/read API is unbuilt. The only write surface is the property/data-room-framed `POST /v1/document-ingest`, and there is no generic memory-put / memory-get / memory-search tool set. Net-new.

Retire-not-overwrite as queryable atom versioning is specced, not implemented. The append-only event log exists, but atom rows have no `retired_at`, `superseded_by`, or `version` columns; supersede and amend live only as graph edge types plus a query-time `asOf` scope hint. "Temporal memory you can read as-of at the atom-row level" is a design, not a shipped query. PROVEN for the absence of the columns. This narrows the placeholder's node/temporal-depth claim: the event chain gives you a verifiable log of what happened, and the interval-query primitive gives you an as-of filter over atoms that carry a `valid_from`, but there is no as-of atom-version materialization the way the placeholder's "what did we know about X in March vs now" implies as a turnkey query.

`atom_events` provisioning is unverified. The contract issues SQL against `atom_events` but ships no migration for it, and no migration creating it was found in the engine repo (004 and 005 create the document and atoms tables only). Whether the table is live in a deployment is UNKNOWN from these repos.

### The domain seam nobody should paper over

`src/property/` (parcel-terrain, setback-rule, zoning-fact) is a cleanly isolated overlay beside the domain-neutral core — good. But the contract's `temporal/node-id.ts` bakes in domain-specific node prefixes (`well_`, `rrclease_`, `tract_`, `oblg_`, `intr_`) for land and oil-and-gas identity derivation. The temporal mechanism is generic; the shipped node types are not. A memory use would define its own node types, which is a schema addition, but it is worth naming that the temporal package as it stands is not domain-clean the way the core registration surface is. PROVEN.

### Section 1 verdict

"Domain-neutral substrate, new schemas" is the correct framing for the contract, the ingest pipeline, the gate's access enforcement, and graph traversal. It is not the full story: the read bridge from ingested atoms to the served atoms, plus a memory-shaped agent API, plus as-of atom versioning, are net-new wiring, not schema additions. The substrate is a genuine domain-neutral cited system-of-record spine whose last mile to "an agent can put/get/search/traverse memory through the gate" is unwired.

## 2. The honest gap — proven-for-property vs. usable-as-memory

Real today, for property, and reusable: content-addressed durable ingest with a generic fallback adapter; the five-value accessPolicy enforced generically at the gate; three-axis asserted confidence on every minted atom; an implemented append-only hash-chain event log; a real, queryable `atom_links` graph with end-to-end traversal; and an as-of interval-query primitive at the contract level.

Would have to be built for memory: the read bridge (ingested atoms into the served StoragePort, or a document-atom read route plus gate tool); a generic memory put/get/search/traverse tool set on the gate; as-of atom-row versioning if "what did we know when" is to be a turnkey query rather than an event-log reconstruction; and confirmation that `atom_events` is provisioned live.

On the placeholder's specific self-checks:

The "read-optimized system-of-record, NOT a Redis-speed scratchpad" claim is confirmed by the write path's actual shape. Ingest is a synchronous HTTP POST that runs the whole pipeline inline — pin, classify, extract, per-atom insert — with no queue, no message bus, no async worker (`services/engine-api/src/routes/document-ingest.ts`, `document-ingest/src/ingest.ts`). Per-document write cost is real: OCR or pdfjs extraction, SHA-256 canonicalization, a GCS save, and up to 500 row inserts. This is durable batch-of-claims ingest, not per-keystroke low-latency. PROVEN in shape; the actual latency number is UNKNOWN (no in-repo benchmark). So the placeholder is right to position at durable long-term system-of-record memory and right to disclaim the high-frequency working-memory scratchpad. That positioning is honest and it matches the code.

The retire-not-overwrite temporal model is partially implemented (event log yes; atom-row versioning no), as above. Do not claim a working retire-not-overwrite over atom rows.

The graph traversal is real, not aspirational — the one place the audit was more positive than the placeholder's hedge.

Net: what is proven for property transfers to memory more cleanly than most "same infra, new domain" claims, because property exercised exactly the domain-neutral surfaces (ingest, CID, accessPolicy, gate, links, history). The honest gap is not "is the substrate domain-neutral" (it is) but "is the memory last mile wired" (it is not).

## 3. Competitive landscape — where we would differ, honestly

Researched against the real market: mem0, Zep/Graphiti, Letta/MemGPT, the commodity vector DBs (Pinecone/Weaviate/pgvector), and the AI-data-room/document-intelligence players (Vectara, Hebbia, Glean). Vendor-site-verified claims are PROVEN; third-party or architecture-reasoned claims are flagged.

The uncomfortable headline: "cited, tenant-sovereign, provenance-carrying memory vs. commodity vector memory" is mostly occupied, not an open gap. It beats mem0 and raw pgvector, but it loses on those exact axes to funded incumbents.

Per-fact provenance to a source is table stakes in the answer/document-intelligence category and present in the strongest memory player. Vectara ships inline citations plus a calibrated 0-to-1 factual-consistency score (PROVEN). Hebbia ships cell-level citation to exact page and paragraph (PROVEN). Glean ships permission-aware cited answers (PROVEN). Zep ships per-fact provenance to the source episode and a bi-temporal knowledge graph that natively answers "what did we know when" (PROVEN) — which is the closest competitor to our node/temporal-depth claim and is the best-funded, most academically-published memory player. Tenant isolation and data sovereignty are likewise table stakes: Zep, Vectara, Hebbia, and Glean all ship real multi-tenant isolation with SOC 2 and often HIPAA (PROVEN). Claiming tenant sovereignty as an edge in a bake-off against these would be embarrassing.

Two claimed differentiators are genuinely unoccupied in the memory market:

Tamper-evidence via content-addressed CID plus hash-chain audit. Nobody in the memory market ships it — Zep, mem0, Letta, Vectara, Hebbia, Glean all have audit logging and encryption, none has content-addressing or a tamper-evident chain (PROVEN-absent across their docs). The only tool found that does ship it (`provena`, an OSS side-project) is a governance/compliance pipeline framed around the EU AI Act, not a memory product. That tells you where the demand actually sits: regulated-AI compliance and defensible records, not "the agent remembers better." So tamper-evidence is a true technical differentiator but a weak commercial one for generic agent builders, who demonstrably do not ask for it. It converts to value only for a buyer who needs cryptographic non-repudiation of a fact's lineage — which is exactly the physical-world jurisdictional / defensible-determination buyer, not the generic memory market.

Calibrated-against-outcome confidence. Unoccupied in the memory market. Vectara's factual-consistency score is the strongest adjacent thing, but it calibrates the generated answer, not a stored fact's reliability tightened against real-world outcome over time (PROVEN distinction). The "confidence earned against outcome, tightening with use" framing (our commitment #2) is genuinely not something these vendors market. But it is a hard thing to prove you have and an easy thing to assert falsely — which is precisely the trap commitment #2 warns about.

On the two framings the operator floated:

The "AI data room" pattern is more occupied, not less. Documents in, cited facts out, tenant-isolated is exactly Hebbia (finance/legal) and Glean (enterprise search) and Vectara (RAG-as-a-service), all funded and shipping. A generic AI data room walks straight into their fire and would be a worse version of Hebbia or Glean unless it wins on a specific vertical corpus. Generic agent memory is also occupied (Zep, mem0, Letta). Neither generic framing is open.

The defensible wedge is neither "generic memory" nor "generic AI data room." It is the intersection the incumbents structurally do not occupy: a domain-specific (physical-world jurisdictional) substrate where atoms carry citation plus calibrated-against-outcome confidence plus tamper-evident lineage, sold as defensible determinations rather than answers or recall. Hebbia and Glean have citation and isolation but no domain corpus and no calibration-against-outcome. Zep has temporal and isolation but no domain corpus, no cryptographic lineage, and unproven confidence. The vector DBs have nothing above the store. The combination is real — but the load-bearing differentiator is the calibrated jurisdictional corpus, with tamper-evidence and citation as the trust features that make the determination defensible, not the reverse.

One verification caveat to carry: whether Zep does calibrated confidence plus source-reliability weighting is NOT confirmed on Zep's own docs (it appears only in a third-party blog). If that claim is real, Zep narrows the gap further. Worth a direct check against Zep's technical docs or arXiv before betting positioning on the confidence axis.

## 4. Go / no-go and the smallest PoC

Recommendation: conditional GO, scoped narrow and honest, gated behind one PoC. Not a general-purpose AI-memory product; not a generic AI data room. Both of those are a worse version of an existing product. The only version worth pursuing is the one that leads with the calibrated, defensible, domain-anchored determination and uses tamper-evident cited memory as the trust substrate underneath it.

Why not a flat no. The reuse is real and the incremental cost to a first honest test is small: a domain-neutral ingest pipeline, a generic fallback adapter, a five-value accessPolicy enforced generically, a real link graph, and an implemented event chain all already exist. The distance to a testable memory surface is one bridge and one thin tool set, not a new platform. That is a cheap enough bet to test rather than kill outright, provided we test the riskiest assumption first and do not fund the product on the strength of a positioning claim the market already contradicts.

Why not a full green. The market read forbids leading with "cited, sovereign, provenance-carrying vs commodity vector memory" — that is table stakes against Zep/Vectara/Hebbia/Glean. And the placeholder's own drop-in optimism is contradicted by the read-bridge gap. So a GO is conditional on repositioning onto the calibrated-domain-corpus-plus-defensible-lineage wedge, and on the PoC clearing.

Spine-rule check. This only earns cycles if it feeds or expresses Hauska. It does, but narrowly: the version that survives is the substrate expressing the same "sell reasoning, not data" thesis pointed at defensible records — which is the substrate thesis (09) generalizing, not a new product line. If it drifts toward generic agent memory, it stops feeding Hauska's actual moat (the calibrated jurisdictional corpus) and should be queued or killed. What gets queued to make room for even the PoC must be named before any build; this doc does not authorize displacing the current property/search/render front-door work.

The riskiest assumption to test. Not "can we ingest arbitrary documents" (proven yes). Not "is the substrate domain-neutral" (proven yes). The riskiest assumption is: does the cited-memory-with-provenance story actually help an external agent produce a better or more trustworthy answer than plain vector search over the same documents — enough that a buyer would pay for the trust properties. If the answer is no, we are a worse vector DB and should stop. The PoC must attack that, cheaply.

### Smallest PoC (tests the riskiest assumption, does not build the product)

Ingest N arbitrary non-property documents (a dozen or two — a real contract set, a diligence folder, a policy corpus, deliberately mixed and messy) through the existing `POST /v1/document-ingest` using the `GenericPdfAdapter` that already ships. Build the one net-new piece the test cannot avoid: the minimal read bridge so those `document_ingest_atoms` are retrievable and traversable through the gate — the smallest of the two options is likely a single document-atom read route plus one gate tool, not a full StoragePort migration. Expose the ingested atoms to an external agent (Claude Desktop or Cursor over MCP) as memory atoms carrying provenance and confidence. Then run the head-to-head: the same agent answering the same questions over (a) the provenance-carrying atom memory vs (b) plain vector search over the identical documents. Measure whether the cited-memory path produces answers that are more correct, more defensible (traceable to a source the user can verify), and less hallucinated — and whether the difference is one a buyer would actually pay for.

What the PoC deliberately does not build: real VDA entitlement (stubbed no-op today per the contract README), the cryptographic anchor (deferred `TODO(M2-C)`), the metering hooks, as-of atom versioning, or any new atom kinds beyond the generic `document-derived-claim` that already exists. Those are product, not proof. If the cited-memory story does not beat plain vector search on trust and defensibility in this cheap test, none of that product work is worth starting.

Kill criterion. If the head-to-head shows no buyer-relevant advantage for cited/provenance memory over plain vector search on this corpus, drop the memory generalization and keep the substrate pointed at the jurisdictional corpus where the calibration moat is real. That is the honest failure mode, and it is cheap to reach.
