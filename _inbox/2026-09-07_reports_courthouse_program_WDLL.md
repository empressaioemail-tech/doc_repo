# Reports + Courthouse Program — WDLL

## Origin

Scoped across one long planning thread that started as a QA review of three
downloaded Smart Site reports (Feasibility Study, X-Ray, Flood & Drainage)
for parcel 48021:47595, and grew into a full architecture read of the report
and chat pipelines, two live cross-session conflict checks against
in-flight lane work, and this card. Courthouse-records integration is
folded in per operator direction ("lets make courthouse part of the reports
program since there is a lot of overlap there") rather than run as a
separate program.

## Done looks like

All four report surfaces (Site Plan, Flood & Drainage, X-Ray, Feasibility
Study) read buildable-envelope and existing-structure facts from one
canonical source and agree with each other on every shared fact, verified
live on at least two real parcels — not merged-and-trusted. Feasibility and
X-Ray narratives are generated by the same LLM engine that already serves
Smart Site's live "Research this" chat (`@workspace/briefing-engine`), with
the deterministic skeleton retained only as the documented, honest fallback
when no citable sentence exists. X-Ray is a defined subset view of the same
underlying Feasibility model rather than a separately-derived assembler,
which is the actual mechanism for tighter cross-document accuracy, not a
patch applied after the fact. Courthouse-retrieved or Smart-Files-mounted
recorded documents can be cited into Feasibility's HOA/recorded-restrictions
section through that same cite-or-decline mechanism. Every defect named in
this thread's QA pass is fixed and re-verified live. The chrome-extension/
Property-Brief front-end is retired, not just superseded in intent.
Feasibility, Flood & Drainage, and X-Ray are all callable from the MCP
companion app the same way Site Plan and dossier already are, so multi-parcel
and portfolio-level research is the companion app's job, not a capability
built into the report engine itself.

**On comprehensiveness** (operator ruling, 2026-09-07): the target is not a
literal match to either Val's 57-sheet Whitetail Ridge package or the
Cude Engineers/Brinkmeyer professional-engineer report used as a comparison
point this session. Both are aspirational reference points, not a checklist
to replicate. What ships should sit alongside them in spirit — real,
citable, useful information a customer can act on — without claiming to be
either document.

## Resolved — multi-parcel scope (operator ruling 2026-09-07, supersedes "Held" above)

**Feasibility stays single-parcel, permanently.** Not deferred, not held —
ruled out of scope for this or any future version of the report engine
itself. Operator's own framing: "we have a claude mcp companion app that is
designed for multi property research... if anything the reports we are
doing need to be callable to the mcp app, that is the highest leverage of
the mcp app, to do this multi parcel coordination." Multi-parcel/portfolio
research is the MCP companion app's job — it orchestrates N single-parcel
report calls itself; the report engine does not need assemblage logic to
serve that use case.

**This surfaced a real, concrete gap, checked directly against the live MCP
tool registry rather than assumed:** Site Plan and X-Ray/dossier both
already have real MCP export tools (`refresh_parcel_site_plan_export` /
`download_parcel_site_plan_export`, `refresh_parcel_dossier_export` /
`download_parcel_dossier_export`, all in `hauska-mcp-server/src/tools.ts`).
**Feasibility has zero MCP tool exposure** — confirmed both here and
independently by the P-32 wave 2 close doc, which named an MCP tool for
feasibility-export as explicitly out of scope, left for hauska-mcp-server's
seat. **Flood & Drainage has no MCP tool either** — not bundled into the
site-plan-export format set, not present anywhere in the tool registry.
Both are PE-web-only today. This is now item 27 below — the actual
mechanism that makes "reports callable to the MCP app" real, not aspirational.
