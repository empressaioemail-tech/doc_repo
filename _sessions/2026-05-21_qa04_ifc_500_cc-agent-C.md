# QA-04 session close — IFC upload

QA-04 was dispatched as "the IFC upload 500." It turned out to be a
four-layer failure. Three layers are diagnosed and fixed; the fourth is
unresolved, is architectural, and caused a brief cortex-api production
outage during verification. Production has been rolled back and is
stable. **QA-04 does not close this session** — the remaining layer is
handed to the next QA cycle as a new backlog item (proposed text at the
end).

## Outcome in one paragraph

The Revit add-in repoint (QA-04 Part 1) works: a real push this session
(Business Park_1_2_3_4) landed its snapshot + 56 sheets in cortex-api
cleanly. The IFC-upload failure (QA-04 Part 2) is four bugs stacked: a
cutover schema gap, a web-ifc module-resolution bug, a container
out-of-memory, and — underneath all of them — an architecture where the
IFC parse runs inline on the api-server's main thread, so a parse that
hangs takes down the whole service. The first three are fixed (one in
the database, two merged as PRs #57 and #58). The fourth is not, and it
means the fixed revision cannot be given production traffic until the
parse is isolated in a worker. Production is on the pre-fix revision;
IFC upload still returns 422 there.

## The four layers

| # | Failure | Symptom | Status |
|---|---|---|---|
| 1 | cortex-prod missing migrations 0009-0014 + the Track B IFC schema | `500` — uncaught DB error on the `snapshot_ifc_files` query | Fixed — migration applied to cortex-prod |
| 2 | web-ifc Node entry resolved via a non-exported subpath | `422 ifc_parse_failed` — `ERR_PACKAGE_PATH_NOT_EXPORTED` | Fixed — PR #57, merged to `main` |
| 3 | web-ifc WASM init exceeds the 2 GiB container limit | `503` — container OOM-killed mid-request | Fixed — PR #58, merged to `main` |
| 4 | IFC parse runs inline on the Node main thread; a hung/trapped parse wedges the whole instance | whole service unresponsive (healthz included) | **Unresolved — architectural** |

### Layer 1 — cutover schema gap (fixed)

`POST /api/snapshots/:id/ifc` 500'd because `ingestSnapshotIfc`'s
unguarded `select … from snapshot_ifc_files` threw uncaught — the table
did not exist on cortex-prod. Investigation (with the doc_repo planner)
established that cortex-prod, the post-cutover production database, was
never migrated past roughly migration 0008: drizzle migrations
0009-0014 (`response_tasks`, L2 sheet content, `deliverable_letters`,
`detail_callout_specs`, `product_spec_references`,
`deliverable_letter_renders`) and the hand-applied
`lib/db/scripts/track-b-ifc-ingest.sql` had never been applied to *any*
production database. cortex-api itself is on the correct database —
`EMPRESSA_DATABASE_URL` is an orphaned, empty, superseded Phase-1B sync
target and was correctly never used.

Fix: applied `drizzle/0009`-`0014` + `track-b-ifc-ingest.sql` to
cortex-prod (`ep-lucky-truth-apodo8hr`, via `psql -f`, every statement
idempotent + additive, all-or-nothing per file). Verified: the IFC 500
flipped to a parse-stage error, and the same migration un-broke the
entire L-surface (response-tasks, detail-callouts, product-specs,
deliverable-letters), which had silently been dark on cortex-prod.

### Layer 2 — web-ifc module resolution (fixed, PR #57)

With the table present the request reached the parse, which failed for
every IFC: `artifacts/api-server/src/lib/ifcParser/wasmRuntime.ts`
resolved the explicit subpath `web-ifc/web-ifc-api-node.js`, which
web-ifc 0.0.71's `exports` map does not expose. PR #57 resolves the
package `.` entry instead (proven to resolve by the line above it).

### Layer 3 — container OOM (fixed, PR #58)

With web-ifc loading, the parse OOM-killed the container: Cloud Run
logged `Memory limit of 2048 MiB exceeded with 2059 MiB used` on a
trivial probe — web-ifc's WASM instantiation alone exhausts 2 GiB.
PR #58 raises the cortex-api Cloud Run memory to 8 GiB.

### Layer 4 — main-thread parse wedges the instance (UNRESOLVED)

The IFC parse runs synchronously inline on the Node main thread, and
`getIfcApi()` is a process-global, non-reentrant `IfcAPI` singleton with
no reset path. Consequences observed live:

- web-ifc's WASM traps (`memory access out of bounds`) on malformed
  input. The trap is caught, but it leaves the cached `IfcAPI` singleton
  corrupt; every subsequent parse on that container instance then fails
  or hangs.
- A parse that hangs blocks the entire Node event loop — the instance
  stops answering everything, healthz included. Cloud Run then sees the
  instance as unresponsive.

This is not a hotfix-sized bug. It is the reason IFC ingest cannot be
made traffic-bearing yet (see the incident below).

## The verification incident

Sequence: the Layer-2/3 fixes were merged and deployed as a 0%-traffic
canary revision (`cortex-api-00014-tab`, 8 GiB). Smoke-probing that
canary, a deliberately malformed IFC trapped web-ifc and a follow-up
probe hit the corrupted singleton and hung — wedging that instance's
event loop. cc-agent-C then recommended shifting production traffic to
that revision without re-confirming the IFC path was healthy
post-probe; the operator shifted, and cortex-api went unresponsive
(healthz timed out). It was rolled back to `cortex-api-00011-xut`,
restoring production within minutes. The bad call — recommending the
traffic shift onto a just-probed revision — is recorded here so the
next cycle does not repeat it: a revision with a live, un-isolated IFC
parse path must not take production traffic.

## Current production state

- cortex-api serves on **`cortex-api-00011-xut`** (rolled back). Stable:
  chat, the L-surface, the SPA, snapshot + sheet ingest all work — the
  operator's live Business Park_1_2_3_4 push confirmed snapshot
  `07d121dc-2442-47cc-b4d2-70c527b566a1` + 56 sheets landed (0 failed).
- **IFC upload returns `422` on `cortex-api-00011-xut`** — that revision
  predates PR #57, so it still hits the web-ifc `exports` error. This is
  expected, not a regression.
- The cortex-prod schema migration **stays applied** — it is additive
  and `cortex-api-00011-xut` runs better against it (the L-surface
  tables it needs now exist). Do not revert it.
- PRs #57 and #58 are **merged to `main`** but the revision that carries
  them must not be given production traffic until Layer 4 is solved.

## Handoff — remaining QA-04 work for the next QA cycle

QA-04 cannot close until the IFC parse is isolated off the api-server
main thread. Proposed backlog item:

> **QA-16. Isolate the IFC parse so a bad IFC cannot wedge cortex-api.**
> The IFC ingest parse (`web-ifc`, `lib/ifcParser`) runs inline on the
> Node main thread with a process-global non-reentrant `IfcAPI`
> singleton. A parse that hangs or traps blocks the whole event loop and
> takes the cortex-api instance down (observed 2026-05-21). Move the
> parse into a `worker_threads` worker (the `ifcParser` module already
> flags this as its intended upgrade) — or a separate Cloud Run service
> — so a crash/hang/OOM kills only the worker and each parse gets a
> fresh WASM context. This is the gate before IFC ingest can take
> production traffic. On completion: deploy the revision carrying
> PRs #57 + #58 + the worker isolation, verify a real Revit IFC returns
> `201` against the canary, then shift traffic. Type: Bug + architecture.
> Workstream: WS-A follow-on. Blocks: QA-04 close.

Lighter robustness follow-ups, worth folding into QA-16 or doing first:

- `ingestSnapshotIfc` has unguarded `await db.*` calls (the `previousRows`
  select, the step-6 update, and `lookupSnapshotForIfc` in
  `snapshots.ts`). A DB error there surfaces as an uncaught HTML 500
  rather than the route's clean `db_error` JSON — that is why Layer 1
  was an opaque 500. Wrap them.
- web-ifc should fail closed on malformed input without corrupting the
  singleton — covered for free once the parse runs in a disposable
  worker.
